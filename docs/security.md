# Security and privacy

## Local-first execution

The managed Obsidian plugin starts a locally bundled SHA-256 verified Node collector under the current OS account, on an ephemeral 127.0.0.1 port. Every request requires a temporary random Bearer token; browser Origin requests are rejected. The token is never saved in Obsidian settings or notes. Data stays in SQLite outside the synced vault unless the user explicitly enables an output.

No analytics telemetry, remote registration, X login extraction, automated likes/follows or default commercial AI provider.

## Source and extension permissions

Each source adapter requires its own provider-authorized access method. Generic ingestion never grants permissions a connector lacks. The bundled public connectors check DNS results and redirects, reject private/internal/loopback addresses and X hosts, pin DNS and enforce response-size/time limits. Public JSON/product inputs require HTTPS; legacy public RSS/metadata can use explicitly configured HTTP, but a redirect from HTTPS cannot downgrade to HTTP. XML DTDs and custom entities are rejected.

The `public-metadata` processor is user opt-in by inclusion in a project pipeline. It performs a bounded number of network requests and never reads X sessions.

**Trusted local .cjs extensions execute arbitrary JavaScript as the current OS user. They are not sandboxed.** Install only modules you have audited; the application does not search for, download or enable extensions by itself. A compromised adapter can reach files and network the current account can access. Isolate third-party code at the operating-system level if greater security is required.

[Extension isolation design](extension-isolation.md) records the threat model, actual controls and requirements for a separate process/capability broker/OS sandbox. The design is complete; an untrusted-code execution backend is not part of this release's supported boundary.

Do not include passwords, cookies or API credentials in synced JSON manifests, note properties, user-provided URLs or source observations. Connector configuration is not persisted raw in the knowledge database (only its fingerprint is saved). Projects can include sensitive data if their source adapter deliberately returns it; choose source mappings carefully.

## Provenance and filesystem safety

Each entity retains observation/connection associations and recorded evidence. Manual approval is separate from automated assessment. Schema and length validation reject malformed, giant or non-JSON data and URL credential parameters.

Namespaced observation entities prevent unrelated providers from sharing an identity accidentally. Existing legacy identities are not renamed, and ambiguous cross-source legacy collisions fail within the page transaction. Persisted replay snapshots are separated from evaluator/processor argument copies so accidental extension mutations do not rewrite the original observation evidence.

The Obsidian output uses safe vault paths and SHA-256 fingerprints to update only previously generated bytes. Unknown or manually edited notes remain untouched; conflicts are reported. The generic engine **never writes to root References.md**. The preserved legacy workflow appends only with human confirmation and a full backup.

## Operational boundaries

- Use Node.js 22.16+ and a current Obsidian Desktop version.
- Back up your vault and local SQLite directory before upgrading.
- Use separate connection IDs for changed source configurations; old cursors cannot be reused silently.
- Respect provider terms, permissions, rate limits and legally required data retention.
- Do not expose the API outside loopback, forward the in-memory token or run untrusted extensions.
- Real-vault integration and personalized X access remain unverified until the user tests them with the correct permissions.

## MCP subprocess boundary

`mcp-stdio` launches an explicit trusted local executable without a shell, terminates the subprocess after a page, and limits response size and execution time. It forwards a minimal OS environment: the collector's `XFS_API_TOKEN` is **not forwarded** by default. `passEnv` can explicitly forward selected OS variables to a trusted MCP tool. A child process is **not sandboxed**: it still has the user's filesystem/network permissions. Never load untrusted MCP servers or grant them private sessions without authorization.

## Guided project creation

The first-run wizard creates unique, create-only manifests under the local per-vault `~/.x-feed-scraper/<vault-hash>/projects/` directory, outside Obsidian vault sync. New files use mode 0600 where supported and directories mode 0700. The bundled demo is synthetic and performs no network request. The wizard validates source URLs, executable choice and optional MCP field mappings before starting a project. A newly created built-in project never automatically inherits a previously configured third-party extension. Changing the active project does not alter the source identifiers or raw records of another project.

The bundled Electron bridge handles numeric browser timers during shutdown; the old unconditional Node-style `.unref()` crash has been fixed. Proper process cleanup prevents duplicate collector instances during restarts.

## Public data monitoring and provenance

`public-json` makes bounded GET requests over HTTPS through the existing DNS-pinned, redirect-revalidated fetcher. `public-product` reads public HTML JSON-LD; it does not evaluate the page's JavaScript, authenticate to merchant accounts or bypass access restrictions. These adapters work only with authorized data sources that expose supported formats; they do not grant permission to scrape every site. Keep URL API tokens and session identifiers out of project manifests. Immutable observation versions can retain historical source text, so treat SQLite backups as sensitive according to your own source data and retention policy. Watch alerts report changes in *observed source claims*, not independently proven prices or actual job closure.

## Explicit external alert delivery

An enabled `webhook` output is a deliberate data transfer to the configured receiver. There is no default receiver and no activation on upgrade. It uses HTTPS POST with DNS/address validation and pinning, rejects every redirect, restricts payload/response sizes and bounds both a request and the overall export. Endpoint URLs and tokens are excluded from delivery errors and the ledger; use environment references for secrets.

The ledger retains the first attempt's payload and a stable idempotency key. Receivers must honor that key because a crash or lost response can cause a repeated request. Current rejection/score policy is checked before every attempt. Status inspection is read-only and never sends data. See [Webhook delivery](webhooks.md).
